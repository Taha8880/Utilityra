# Utilityra — المرجع الشامل للموقع وخطة المهندس التقني بالذكاء الاصطناعي

> **آخر مراجعة للمستودع:** 23 أكتوبر 2026  
> **الغرض:** مرجع تنفيذي واحد يشرح بنية Utilityra الحالية، ما تم تنفيذه، الأعطال المعروفة، طريقة تشخيصها وإصلاحها، لوحة الإدارة، الذكاء الاصطناعي، الأمن، الاختبارات، وخطة التطوير.  
> **قاعدة الدقة:** هذا المستند يفرّق بين ما يثبته الكود أو سجلات CI، وما هو مخطط أو يحتاج تحققًا حيًا. وجود ملف أو إعداد لا يعني أن الميزة مفعّلة أو ناجحة على الموقع العام.

## 1. ملخص تنفيذي

Utilityra منصة أدوات عملية بالعربية والإنجليزية. الإصدار النشط الذي يجري تطويره ونشره حاليًا هو تطبيق Cloudflare Worker، وليس ملفات Blogger القديمة.

- الموقع العام: https://utilityra.tavengers16.workers.dev/
- لوحة الإدارة: https://utilityra.tavengers16.workers.dev/admin
- مستودع الكود: https://github.com/Taha8880/Utilityra
- الواجهة: `worker/public/index.html`
- Worker والـ API: `worker/src/index.js`
- لوحة الإدارة الخاصة: `worker/public/admin.html`
- قاعدة D1 ومخططها: `worker/schema.sql` و`worker/seed.sql`
- النشر: `.github/workflows/deploy-worker.yml`
- التحقق من سجل الأدوات: `scripts/validate-cloudflare.mjs`
- اختبارات الأدوات: `tests/e2e/cloudflare-tools.spec.js` و`tests/e2e/tool-accuracy.spec.js`
- عدد صفحات الأدوات المسجلة في آخر تحقق للكود: **52 أداة**.

**الحالة العامة:** يوجد أساس فعلي للموقع، وواجهة أدوات، وWorker API، وD1، ولوحة إدارة خاصة، وتحليلات أولية، وبوابة AI بثلاثة مزودين محتملين، واختبارات تلقائية. لكن لا يجوز وصف كل شيء بأنه مكتمل: آخر تشغيل متصفح مكتمل رُصد فيه فشل في اختبارات لبعض الأدوات على الكمبيوتر والموبايل، ثم أُرسلت إصلاحات وتشغيلات أحدث؛ يجب انتظار نتيجة أحدث تشغيل كامل ناجح قبل إعلان اجتياز المجموعة كلها. كما أن جودة التصميم تحتاج مراجعة مرئية حقيقية، لا مجرد نجاح النشر.

## 2. مصدر الحقيقة وتجنب خلط المشاريع

### الملفات الفعالة حاليًا
- الواجهة والأدوات: `worker/public/index.html`.
- منطق الطلبات وواجهات API والأمان: `worker/src/index.js`.
- مخطط البيانات: `worker/schema.sql`.
- نشر Worker وD1 والأسرار: `.github/workflows/deploy-worker.yml`.
- اختبارات المتصفح: `tests/e2e/`.

### الملفات القديمة
يحتوي المستودع أيضًا على `blogger-pages/` وملفات قوالب Blogger وعمليات مزامنة قديمة. احتُفظ بها كآثار تاريخية/مرجعية، لكنها **ليست هدف نشر واجهة Cloudflare الحالية**. بعض الوثائق القديمة لا تزال تذكر Blogger أو أسماء تجريبية مثل Flarivo وبيانات إعداد غير متوافقة مع التطبيق الحالي؛ يجب تحديثها تدريجيًا لتشير إلى Utilityra وCloudflare، وعدم استخدامها كمرجع نشر حالي إذا تعارضت مع هذا المستند أو مع الكود الفعلي.

**قاعدة عمل:** أي تعديل للموقع الحالي يبدأ من `worker/`، ثم التحقق، ثم اختبارات المتصفح، ثم النشر. لا تُرفع قوالب Blogger القديمة لتصحيح موقع Cloudflare.

## 3. خريطة النظام

```text
المستخدم / متصفح الهاتف أو الكمبيوتر
        |
        v
Cloudflare Worker + Static Assets
  |        |          |           |
  |        |          |           +--> صفحات الأدوات وملفات SEO
  |        |          +--------------> بوابة AI: /api/ai
  |        +-------------------------> تحليلات ولوحة الإدارة الخاصة
  +----------------------------------> D1: بيانات/إحصاءات/محاولات دخول
        |
        +--> OpenAI (اختياري عبر سر)
        +--> Gemini (اختياري عبر سر)
        +--> Workers AI (يتطلب binding)
        +--> GDELT للبحث عن تغطية إخبارية حديثة عند الحاجة
```

- **المتصفح:** مناسب للأدوات التي تعالج النصوص والصور وملفات PDF محليًا متى كان تنفيذ الأداة يؤكد ذلك.
- **Worker:** المكان الصحيح للأسرار، والتحقق، والحدود، وتوجيه طلبات AI، والتحليلات، والعمليات التي تتطلب الخادم.
- **D1:** تخزين منظم للتحليلات وسجلات البيانات ومحاولات دخول الإدارة.
- **GitHub Actions:** تحقق تلقائي ونشر واختبارات.
- **المزود الخارجي:** لا يضمن وحده صحة النتيجة؛ يلزم فحص المدخلات والمخرجات ومصادر الحقائق والحدود والتكلفة.

## 5. التصميم وتجربة الاستخدام

المشكلات التي أبلغ عنها صاحب الموقع:
- عدم تناسق شكل الصفحة والبطاقات.
- تداخل أو تزاحم الحروف العربية وظهور حروف زائدة بصريًا.
- عدم توحيد أحجام العناوين والنصوص.
- تصميم الأيقونات غير مرضٍ.
- تفاوت ارتفاع البطاقات والمسافات.
- ضرورة أن تعمل العربية RTL والإنجليزية LTR بشكل صحيح على الهاتف والكمبيوتر.

التغييرات التي نُفذت في آخر تحديثات الواجهة:
- إضافة قواعد CSS لتقليل تباعد الحروف العربية وضبط ارتفاع السطر.
- ضبط أحجام ومسافات البطاقات في نقاط توقف للشاشات الكبيرة والمتوسطة والصغيرة.
- استبدال الرموز المختلطة في بطاقات الأدوات بأيقونات SVG موحدة ذات stroke متناسق.
- تحسين التفاف النصوص ومنع تمدد البطاقات خارج الشبكة.
- تحسين ألوان ومسافات لوحة الإدارة وإضافة تنقل داخلي للأقسام.

**ما لم يثبت بعد:** لا يكفي أن تُحفظ التعديلات أو ينجح النشر. يلزم اختبار مرئي فعلي على Android Chrome وكمبيوتر، بالعربية والإنجليزية، مع فحص: التشكيل والحروف العربية، تباعد الأسطر، تداخل الأيقونات، بطاقات بعناوين قصيرة وطويلة، أحجام 320–390px، الوضع الفاتح، لوحة الإدارة، والنوافذ المنبثقة. لا تعتبر التصميم مقبولًا حتى تُفحص لقطات الشاشة وتُحل العيوب المرئية.

### معيار التصميم المطلوب
- خط عربي واضح، وخط لاتيني متناسق، من دون `letter-spacing` سلبي للعربية.
- مقياس خطوط ثابت: عنوان رئيسي، عنوان قسم، عنوان بطاقة، وصف، نص مساعد، ورسالة خطأ.
- ارتفاع سطر مناسب للعربية، وعدم قص الحروف أو التشكيل.
- شبكة بطاقات ثابتة؛ الأيقونة والعنوان والوصف وزر الفتح بمحاذاة منتظمة.
- مجموعة SVG واحدة بأحجام وسمك خطوط متناسق، لا خليط emoji.
- اتجاه RTL/LTR حسب اللغة، وأزرار وحقول سهلة اللمس على الهاتف.
- حالات واضحة للتحميل والنجاح والخطأ والنتيجة الفارغة.
- احترام `prefers-reduced-motion`، وتباين قابل للقراءة، وتركيز لوحة المفاتيح.

## 6. لوحة الإدارة الشاملة

الرابط: `/admin`. الصفحة خاصة وغير مخصصة للفهرسة، ولا ينبغي ربطها في قائمة الموقع العامة.

### وظائف موجودة في الكود
- تسجيل دخول يتحقق من كلمة المرور في الخادم.
- جلسة موقعة عبر cookie بخصائص HttpOnly وSecure وSameSite=Strict، وتنتهي بعد مدة محددة.
- الحد من محاولات تسجيل الدخول الفاشلة.
- إحصائيات آخر 30 يومًا: الزوار التقديريون، الأحداث، الزيارات اليومية، الصفحات الأكثر زيارة، الأدوات الأكثر استخدامًا، وعمليات البحث التي لم تجد أداة.
- اقتراح أدوات جديدة بالذكاء الاصطناعي اعتمادًا على بيانات الموقع الداخلية فقط، مع حد أدنى 20 حدثًا مؤهلًا، ومن دون ادعاء معرفة حجم البحث الخارجي.
- روابط تشخيصية إلى sitemap وrobots وhealth والصفحات العامة.
- استبعاد زيارات صاحب الموقع من التحليلات عبر اختيار في المتصفح؛ يجب تطبيقه على كل جهاز/متصفح يستخدمه المالك.

### ما لا ينبغي الادعاء بأنه موجود تلقائيًا
- ليست لوحة إدارة كاملة لتعديل جميع الصفحات أو تعديل قاعدة البيانات أو إدارة المستخدمين.
- لا تنشر أدوات جديدة ولا تعدل الكود أو إعدادات Cloudflare تلقائيًا.
- فحص استجابة sitemap أو robots لا يثبت أن Google قبل الفهرسة.
- بيانات الزوار تقديرية وتعتمد على أحداث الطرف الأول، وليست عدًّا مؤكدًا لكل شخص.
- استبعاد الروبوتات والمراجعات الآلية تقريبي ولا يمكن ضمان معرفة هوية كل زائر آلي.

### إضافات مقترحة للوحة الإدارة بالترتيب
1. **حالة الخدمات:** Worker وD1 ومزودو AI وتاريخ آخر نشر وآخر نجاح اختبار.
2. **صحة الموقع:** آخر نتيجة لاختبارات الكمبيوتر والهاتف، وعدد الفشل وأسماء الاختبارات الفاشلة، وآخر Lighthouse.
3. **مركز الأعطال:** سجل آمن للأخطاء مع رمز خطأ، المسار، الوقت، وشدة العطل؛ دون كلمات مرور أو مفاتيح أو نصوص المستخدم.
4. **إدارة الفهرسة:** حالة HTTP لـ sitemap/robots/الصفحات الأساسية، وآخر وقت فحص، مع رابط إلى Search Console. لا تكتب "مفهرس" دون بيانات Google فعلية.
5. **إدارة AI:** مزود افتراضي، حالة الإعداد، النموذج، حدود الاستخدام، الأخطاء، وتكلفة تقديرية إذا توفرت بيانات موثوقة.
6. **إدارة الأدوات:** فهرس الحالة (مفعلة/معطلة/تحتاج مراجعة)، إصدار الأداة، آخر اختبار، ومشاكل معروفة.
7. **اقتراحات الذكاء الاصطناعي:** حفظ كل اقتراح مع الدليل والثقة وخطة الاختبار، ثم موافقة المالك.
8. **سجل التغييرات:** commit SHA، نتيجة CI، نتيجة النشر، ومن وافق على الإصدار.

لا تُضف زرًا يوحي بأنه يصلح أو ينشر شيئًا ما لم يكن متصلًا فعلًا بتنفيذ آمن ومختبر.

## 7. الذكاء الاصطناعي: الوضع الحالي

### بوابة AI الموجودة
- المسار: `POST /api/ai`.
- المزودات المدعومة في الكود: OpenAI، Gemini، وCloudflare Workers AI.
- النموذج الافتراضي المكتوب في الكود:
  - OpenAI: `gpt-4.1-mini`
  - Gemini: `gemini-2.5-flash`
  - Workers AI: `@cf/meta/llama-3.1-8b-instruct`
- يحد الكود طول الرسالة والسياق، ويتحقق من المزود والمدخلات، ويعيد أخطاء مفهومة عند غياب الإعداد أو تجاوز حدود المزود.
- إذا كان السؤال عن معلومات حديثة، يحاول البحث في GDELT وإرفاق عناوين وروابط كدليل. هذا ليس ضمانًا لصحة كل خبر، ولا بد من فحص المصدر.
- لوحة الإدارة تستخدم AI لاقتراح أفكار أدوات من تحليلات آخر 30 يومًا فقط؛ ويُشترط 20 حدثًا مؤهلًا، وتبقى الاقتراحات بحاجة إلى موافقة المالك.

### كيف تختار أفضل مزود؟
لا يوجد مزود أفضل في كل شيء. الاختيار العملي المقترح:

| الاستخدام | الخيار المفضل | السبب والحدود |
|---|---|---|
| مساعد الموقع العام بتكلفة مضبوطة | ابدأ بـ Workers AI إذا كان binding مفعلًا ونتائجه كافية | تكامل Cloudflare أسهل ولا يحتاج مفتاح API خارجي؛ الجودة والحدود تعتمد على النموذج والخطة |
| مهام البرمجة المعقدة وتحليل السجلات | OpenAI كخيار متميز بعد اختبار النموذج الفعلي | مناسب كبوابة مساعد قوية؛ يحتاج مفتاحًا سريًا ومراقبة الاستخدام والتكلفة |
| بديل سريع/احتياطي | Gemini Flash | بديل مدعوم بالكود؛ يحتاج مفتاحًا سريًا وحدود استخدام |
| اقتراح أدوات من التحليلات | استخدم المزود الأقل تكلفة الذي ينجح في اختبار JSON والالتزام بالأدلة | لا يحتاج النموذج إلى بيانات شخصية أو نصوص المستخدمين |

**التوصية العملية:** لا تُفعّل المزودات الثلاثة دون حاجة. ابدأ بمزود أساسي واحد واختبره، ثم أضف مزودًا احتياطيًا إذا كانت هناك حاجة فعلية. كود التقرير الحالي يفضّل OpenAI ثم Gemini ثم Workers AI عند توليد اقتراحات الإدارة إذا كانت متاحة، بينما طلب `/api/ai` يحدد المزود صراحةً. يجب توحيد هذه السياسة في إعداد واضح بدل أن تكون الأولوية ضمنية في أكثر من موضع.

### إعدادات وأسرار النشر
أسماء أسرار GitHub Actions التي يقرأها مسار النشر:
- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`
- `UTILITYRA_ADMIN_PASSWORD` — 16 حرفًا على الأقل.
- `UTILITYRA_ADMIN_SESSION_SECRET` — 32 حرفًا على الأقل.
- اختياري: `UTILITYRA_OPENAI_API_KEY`
- اختياري: `UTILITYRA_GEMINI_API_KEY`

مسار النشر ينسخ المفاتيح الاختيارية إلى أسرار Worker بأسماء `OPENAI_API_KEY` و`GEMINI_API_KEY`. أما Workers AI فيحتاج binding باسم `AI`؛ وجود كود يستدعي `env.AI.run` لا يثبت أن الـ binding مفعّل في بيئة الإنتاج. يجب فحص `/health` للتأكد من أعلام التهيئة، دون كشف قيم الأسرار.

**ممنوع:** وضع مفاتيح AI في HTML أو JavaScript للمتصفح أو المستودع أو التقرير. لا ترسل كلمات المرور أو المفاتيح داخل المحادثات. إذا فشل إعداد الأسرار، أصلح إعداد GitHub/Cloudflare من واجهة الخدمة، ثم أعد النشر.

## 8. كيف يصبح الذكاء الاصطناعي «مهندسًا تقنيًا» للموقع؟

يجب أن يكون المقصود **وكيل هندسة برمجيات مراقَب** وليس روبوتًا يغيّر الإنتاج دون مراجعة. النموذج وحده لا يملك صلاحية تعديل GitHub أو تشغيل الاختبارات إلا إذا رُبطت به أدوات تنفيذ وصلاحيات محددة.

### المستوى 1 — المساعد الحالي
- يشرح الأعطال ويقترح حلولًا.
- يساعد في فهم السجلات والكود.
- يجيب عبر مزود AI من خلال Worker.
- يقترح أدوات جديدة بناءً على بيانات داخلية عند توفرها.
- لا يملك وحده صلاحية تنفيذ الإصلاحات أو النشر.

### المستوى 2 — مهندس التشخيص
أضف خدمة داخلية تقرأ، بصلاحيات محدودة:
- نتائج GitHub Actions وآخر commits.
- تقارير Playwright وLighthouse.
- أخطاء Worker المنقّحة.
- صحة D1 ومزود AI وواجهات API.
- سجل الإصدارات والتغييرات.

وتنتج تقريرًا موحدًا: المشكلة، دليلها، مدى الثقة، السبب المرجح، خطوات إعادة الإنتاج، الملفات المحتمل تأثرها، الاختبار الذي يثبت الإصلاح، وخطة التراجع. لا ترسل أسرارًا أو مدخلات المستخدم إلى النموذج.

### المستوى 3 — مهندس إصلاح في بيئة معزولة
- ينشئ فرعًا مستقلًا لكل إصلاح.
- يعدل الملفات ضمن قائمة مسموح بها.
- يضيف اختبارًا يثبت المشكلة قبل إصلاحها.
- يشغّل syntax/registry/unit/Playwright/accessibility/security checks.
- ينشئ Pull Request مع diff ونتائج الاختبارات ومخاطر التغيير.
- يمنع الدمج إذا فشل اختبار أو كان التغيير غير واضح.
- لا يملك صلاحية تعديل أسرار الإنتاج أو حذف البيانات أو تغيير إعدادات الحساب.

### المستوى 4 — إصدار بموافقة المالك
- بعد موافقة بشرية صريحة على الـ PR، تسمح سياسة النشر بنشره.
- بعد النشر يجري smoke tests على الموقع العام.
- إذا فشل فحص حاسم، يوقف الترويج للإصدار أو ينفذ rollback مدروسًا إن كانت آلية الرجوع مختبرة.
- يسجل commit، ووقت النشر، والاختبارات، والنتيجة، ولا يدّعي النجاح دون دليل.

### المستوى 5 — مراقبة وتحسين مستمران
- تنبيه عند تكرر فشل Worker أو فشل اختبار أو تعطل مزود AI.
- تقرير يومي/أسبوعي مختصر بالمشاكل الفعلية، لا تقارير مولدة بلا بيانات.
- تحليل طلبات الأدوات المفقودة واقتراح تحسينات.
- قياس الأداء وإمكانية الوصول وتجربة الهاتف قبل وبعد الإصلاح.
- لا يضيف أدوات كثيرة لمجرد زيادة العدد؛ كل أداة جديدة تحتاج دليل حاجة واختبارًا وخطة صيانة.

### الصلاحيات التي يجب عدم منحها للوكيل
- لا يقرأ أو يعرض الأسرار.
- لا يدمج أو ينشر تغييرًا عامًا دون موافقة صريحة.
- لا ينفذ أوامر مدمرة أو يحذف قاعدة البيانات.
- لا يجلب URL يحدده المستخدم من الخادم دون allowlist؛ لتجنب SSRF.
- لا يثق بمخرجات AI أو محتوى صفحات الإنترنت باعتبارها تعليمات.
- لا يختبر أنظمة لا يملكها الموقع أو لا توجد موافقة لاختبارها.
- لا يغيّر SEO أو الخصوصية أو سياسة الإعلانات دون مراجعة.

## 9. المشكلات والأعطال المعروفة وطريقة حلها

### أ. التصميم والخط العربي
**العَرَض:** حروف متداخلة، أحجام غير متناسقة، بطاقات متفاوتة، وأيقونات غير متجانسة.  
**الإجراء المنفذ:** CSS لضبط line-height وletter-spacing للعربية، شبكة بطاقات متجاوبة، وأيقونات SVG موحدة.  
**المتبقي:** مراجعة لقطات فعلية للموبايل والكمبيوتر، وتصحيح أي قصّ/تداخل في العناوين الطويلة.  
**التحقق:** 320px و360px و390px و768px وشاشة كمبيوتر، بالعربية والإنجليزية؛ اختبر عناوين قصيرة وطويلة وأوصافًا متعددة الأسطر.

### ب. اختبارات المتصفح غير ناجحة بالكامل
في تشغيل متصفح أقدم سُجل 69 نجاحًا و10 حالات فشل وحالة flaky واحدة. وفي تشغيل أحدث على commit `b0eac34e` تحسنت النتيجة إلى **78 اختبارًا ناجحًا وفشلين**، وكان الفشلان في اختبار تبديل اللغة الذي يتحقق من نصوص فلاتر التصنيفات وبطاقات الأدوات على الكمبيوتر والموبايل. شملت الأعطال التي ظهرت في التشغيل الأقدم:
- محلل CSV مع الفواصل والاقتباسات المهروبة.
- تحويل النص وأنظمة الأعداد والألوان.
- حساب العمر.
- تبديل اللغة وفلاتر التصنيفات والبطاقات.
- اختبار Base64 لنص عربي UTF-8.
- اختبار دمج PDF كان flaky بسبب اختبار رابط تنزيل blob.

أُرسلت لاحقًا تغييرات إصلاح للترميز/الحساب العلمي وتنزيل PDF، ثم تغيير لتعديل توقع اختبار التصنيف. كان تشغيل المتصفح على commit `c24df769` قيد التنفيذ وقت إعداد هذه المراجعة، لذلك **لم يتم بعد تأكيد نجاح أحدث مجموعة كاملة على الكمبيوتر والموبايل**.

**طريقة الحل:** فتح أحدث GitHub Actions، تحديد أول فشل حقيقي، مراجعة trace/screenshot، إعادة إنتاجه، إصلاح المنطق أو الاختبار (لا تخفِ فشل المنتج بتخفيف التوقعات)، ثم إعادة تشغيل الاختبارات. اختبر البيانات العربية والفواصل والاقتباسات والحدود الرقمية والملفات الفعلية.

### ج. فشل مزود AI أو غياب إعداداته
**الأعراض المحتملة:** `PROVIDER_NOT_CONFIGURED` أو `AI_PROVIDER_NOT_CONFIGURED` أو 429 أو 502.  
**طريقة التشخيص:**
1. افتح `/health` وتحقق من أعلام `openaiConfigured` و`geminiConfigured` و`workersAIConfigured` و`dataStoreConfigured`.
2. إذا كان المفتاح غائبًا، راجع أسماء GitHub Actions secrets بدقة، ثم شغّل workflow النشر.
3. إذا كان Workers AI غير مفعّل، تحقق من binding `AI` في إعدادات Worker.
4. إذا ظهر 429، افحص حدود المزود ولا تعاود الطلبات بلا حدود.
5. إذا ظهر 502، افحص سجلات Worker ورمز الاستجابة من المزود دون تسجيل المفتاح أو prompt الحساس.
6. اختبر كل مزود بمطالبة بسيطة ثم حالة عربية ثم حالة خطأ. لا تعتبر وجود مفتاح وحده إثباتًا لجودة الرد.

### د. لوحة الإدارة لا تفتح أو لا تسجل الدخول
1. تحقق أن `/admin` يعرض الصفحة و`/api/admin/session` يرجع الحالة المتوقعة.
2. تحقق من أسرار `UTILITYRA_ADMIN_PASSWORD` و`UTILITYRA_ADMIN_SESSION_SECRET`، وطول كل منهما.
3. تأكد أن النشر انتهى بنجاح وأن `ASSETS` وD1 مربوطان.
4. تحقق أن `/api/admin/stats` يرفض الجلسة غير المصرح بها بـ401.
5. اختبر كلمة مرور خاطئة وتكرار المحاولات، ثم دخول صحيح وتسجيل خروج.
6. امسح جلسة المتصفح فقط إذا كانت منتهية أو تالفة؛ لا تعطّل خصائص cookie الأمنية كحل سريع.

### هـ. التحليلات لا تظهر
- يجب أن يكون D1 مربوطًا وأن يكون schema قد طُبق بنجاح.
- تحقق من وصول أحداث `/api/analytics/event` ومن صحة origin.
- لا تتوقع أرقامًا قبل وصول أحداث مؤهلة، ولا تتوقع اقتراحات AI قبل 20 حدثًا.
- تحقق من عدم تفعيل استبعاد زيارات المالك على المتصفح الذي تستخدمه للاختبار.
- لا تحفظ IP الخام أو نصوص الملفات أو مدخلات الأدوات في سجلات التحليلات.

### و. صفحات الأدوات ترجع 404 أو تعرض الصفحة الخطأ
- تأكد أن slug موجود في سجل `T` وفي `INDEXABLE_TOOL_SLUGS` عند الحاجة، وأن اختبار `SLUGS` يغطيه.
- شغّل `node scripts/validate-cloudflare.mjs`.
- اختبر `/tools/<slug>` وتأكد من HTTP 200 وعنوان أداة صحيح، لا مجرد الصفحة الرئيسية.
- إذا أضفت أداة، حدّث السجل والاختبارات والـ SEO metadata وتعليمات الأداة في نفس التغيير.

### ز. ملف PDF لا يُقرأ أو لا يعمل
- `pdf-to-text` يستخرج النص القابل للتحديد فقط؛ لا يحتوي OCR للملفات المصورة.
- الحد الموثق: 25 MB و250 صفحة.
- قد تحتاج مكتبة PDF إلى الاتصال بالـ CDN؛ اختبر الشبكة وCSP وWorker script.
- اختبر ملف PDF نصي، وملفًا مصورًا، وملفًا تالفًا، وملفًا كبيرًا، وتأكد من رسائل الخطأ.
- لا تعرض وعد OCR ما لم تُضف محرك OCR وتختبره فعليًا.

### ح. API tester لا يتصل بخادم خارجي
قد يمنع الخادم المستهدف طلبات المتصفح عبر CORS؛ هذا لا يعني بالضرورة أن الخدمة معطلة. وضّح للمستخدم السبب ولا تنشئ proxy عامًّا يجلب أي URL. أي proxy خادمي يجب أن يستخدم allowlist ومهلًا وحدودًا للحجم ومكافحة SSRF.

### ط. PageSpeed / Google / الفهرسة
- PageSpeed Insights قد يفرض rate limits أو يفشل إذا لم تتوفر الحصة.
- نجاح `sitemap.xml` أو `robots.txt` في الرد يعني أن المسار يجيب فقط، لا أن Google فهرس الصفحات.
- إثبات الملكية يجب أن يستخدم الطريقة الصحيحة والمحتوى الموجود في المسار الجذري الفعلي، وأن يتم التحقق من عنوان الموقع المطابق.
- بعد النشر: افحص HTTP، canonical، sitemap، robots، العناوين والأوصاف، ثم تابع تقارير Search Console. لا تكرر طلبات التحقق عند تجاوز الحصة؛ انتظر تجددها أو أصلح طريقة التحقق.
- لا يمكن ضمان ترتيب البحث أو قبول AdSense بواسطة الكود وحده.

### ي. فشل النشر أو CI
1. اقرأ أول خطوة فاشلة في workflow، لا آخر رسالة فقط.
2. افصل بين فشل التحقق، وفشل النشر، وفشل smoke test، وفشل اختبار المتصفح.
3. لا تعتبر النشر ناجحًا إذا كان workflow قد أُلغي أو ما زال قيد التشغيل.
4. راجع إعدادات GitHub secrets وCloudflare permissions وD1 وWorker bindings.
5. بعد أي تغيير واجهة، انتظر اكتمال deploy ثم افتح الموقع المنشور واختبره.

### ك. وثائق قديمة أو متناقضة
بعض ملفات docs القديمة تحتوي أسماء مشروع قديمة أو خطوات Blogger أو placeholders لا تطابق الواجهة النشطة. الحل هو اعتماد هذا المرجع، ثم توحيد الوثائق الأخرى على مراحل، مع إبقاء تعليمات Blogger في قسم واضح بعنوان Legacy فقط وعدم حذف ملفات تاريخية قبل التحقق من عدم استخدامها في workflow.

## 10. الخصوصية والأمن

- الأسرار في GitHub Actions/Cloudflare Secrets فقط.
- `/admin` يجب أن يبقى noindex وغير مرتبط من الصفحة العامة، مع تحقق صلاحية على الخادم لكل endpoint إداري.
- تحليلات الطرف الأول لا ينبغي أن تخزن IP الخام أو user-agent كاملًا أو ملفات المستخدم أو نص المدخلات.
- تقليل حجم الطلبات والتحقق من JSON وطول الرسائل قبل إرسالها إلى AI.
- ضع rate limiting/quotas على AI قبل توسيع الوصول العام.
- اعتبر مدخلات المستخدم والصفحات المسترجعة ومخرجات AI بيانات غير موثوقة.
- هرب النص قبل إدخاله في HTML؛ لا تستخدم `innerHTML` مع بيانات غير موثوقة من دون sanitization موثوق.
- استخدم allowlist لأي مصدر خارجي أو crawler؛ امنع الوصول إلى عناوين الشبكات الداخلية وخدمات metadata.
- لا تعرض تفاصيل الأسرار في `/health` أو logs؛ يكفي Boolean أو رمز خطأ.
- راجع سياسة الخصوصية لتطابق التحليلات الفعلية ومزودي AI والاحتفاظ بالبيانات.

## 11. مصادر البيانات ومركز المعرفة

يوجد مخطط D1 لمصادر البيانات والمجموعات والسجلات وعمليات الاستيراد والتغذية الراجعة والتحليلات ومحاولات الدخول. تبدأ سجلات seed بحالة draft، والمجموعات خاصة. يجب عدم تحويل أي مجموعة إلى عامة أو وضع سجل على verified إلا بعد التأكد من المصدر والترخيص والتاريخ.

- فضّل API رسميًا أو RSS/Atom مسموحًا به قبل كشط HTML.
- احتفظ باسم المصدر والرابط والترخيص وتاريخ الجلب والتحقق.
- خزّن العناوين والملخصات القصيرة والروابط عند الحاجة، لا تنسخ المقالات كاملة.
- استخدم deduplication وtimeouts وcaching وlimits.
- GDELT يستخدم لاكتشاف تغطية عامة حديثة؛ لا يساوي تحققًا صحفيًا ولا يثبت صحة العناوين.
- لا توصل Context7 أو Strix أو Scrapling أو ScrapeGraphAI أو MCP Agent Reach تلقائيًا إلى واجهة المستخدم العامة. هذه أدوات تطوير/اختبار اختيارية، وبعضها غير متصل أو لم يُختبر بعد. أي اختبار أمني يجب أن يكون على نطاق مملوك ومصرح به.

## 13. خطة تنفيذ ذات أولوية

### P0 — قبل إعلان الموقع مستقرًا
1. انتظار أحدث CI ثم إصلاح كل فشل متبقٍ من الاختبارات، لا الاكتفاء بإنشاء commits إصلاح.
2. مراجعة بصرية للواجهة العربية/الإنجليزية على الهاتف والكمبيوتر وتصحيح العيوب المرئية.
3. اختبار جميع المسارات المسجلة، ثم اختبار سلوك الأدوات ذات المخاطر الأعلى (CSV/JSON/Base64/PDF/الحسابات/اللغة).
4. اختبار لوحة الإدارة والأسرار وD1 وAI provider من البيئة المنشورة.
5. توثيق آخر commit منشور ورابط run ناجح.

### P1 — إدارة احترافية
1. صفحة حالة للخدمات والاختبارات والنشر.
2. سجل أخطاء آمن مع correlation ID ووقت ومسار ورمز خطأ.
3. إظهار حالة مزود AI الفعلية وحدود الاستخدام من دون كشف أسرار.
4. اختبار آلي للـ visual regressions ومقاسات الشاشة.
5. فحص أمان واعتمادات دوري وتنبيه للأعطال المتكررة.

### P2 — المهندس التقني بالذكاء الاصطناعي
1. جمع بيانات التشخيص من GitHub Actions وWorker وLighthouse بصورة آمنة.
2. إنتاج تقارير مشكلة + دليل + سبب مرجح + اختبار إصلاح.
3. إنشاء branch وPR فقط في sandbox وبصلاحيات محدودة.
4. تشغيل الاختبارات تلقائيًا، وإرفاق النتائج والـ diff.
5. اشتراط موافقة بشرية قبل merge/deploy.
6. متابعة بعد النشر والتحقق من صحة الإصدار، مع rollback مختبر عند الضرورة.

### P3 — النمو والبحث
1. ربط Search Console بقراءة مصرح بها لبيانات الأداء الحقيقية.
2. فصل بيانات البحث الداخلي عن بيانات Google.
3. تطوير الكتالوج بناءً على طلبات فعلية وأدلة، لا التخمين.

## 15. تعريف النجاح النهائي

لا تُعتبر Utilityra مكتملة لمجرد أنها تفتح. تعتبر مستقرة عندما:
1. تظهر الحروف العربية والإنجليزية بوضوح دون تداخل على الأجهزة المستهدفة.
2. تكون الأيقونات والبطاقات متناسقة ويمكن استخدام الموقع بلوحة المفاتيح واللمس.
3. تعمل الأدوات فعليًا وتنجح اختبارات الدقة والحدود والأخطاء.
4. تكون الإدارة خاصة، والتحليلات صحيحة بقدر ما تسمح به طريقة القياس، والأسرار محمية.
5. يعمل AI عبر مزود محدد بوضوح، مع حدود تكلفة ورسائل خطأ صادقة.
6. ينجح التحقق والنشر واختبار ما بعد النشر، وتوجد خطة رجوع.
7. تكون توصيات AI مبنية على بيانات، ولا تُنشر التغييرات البرمجية إلا بعد اختبارات وموافقة المالك.

**المبدأ الأساسي:** Utilityra مشروع أدوات وخدمات موثوق، وليس مجرد عدد كبير من الصفحات أو واجهة تبدو جميلة. كل ميزة يجب أن تكون مفهومة، قابلة للاختبار، آمنة، ومسنودة بدليل عند وصفها بأنها تعمل.


## 13. سجل المتطلبات والتحديث التلقائي والمراقبة

الملفات التالية داخل المستودع، ولذلك تدخل ضمن ZIP:

- `docs/UTILITYRA_REQUIREMENTS_AR.md`: المتطلبات المعتمدة وحالة التنفيذ وما يحتاج دليلًا إضافيًا.
- `docs/STATUS_LATEST_AR.md`: تقرير حالة مولّد تلقائيًا يتضمن آخر commits ونتائج GitHub Actions وفحوصات HTTP عامة.
- `scripts/update-project-status.mjs`: مولّد التقرير الآلي.
- `.github/workflows/utilityra-continuous-record.yml`: يحدّث سجل الحالة بعد تغييرات main وبعد اكتمال workflows المختارة، وبجدولة كل ست ساعات.
- `.github/workflows/utilityra-live-monitor.yml`: يفحص الصفحة الرئيسية وrobots وsitemap ومسارين للأدوات كل 30 دقيقة، وينشئ GitHub Issue عند الفشل لتسجيل الحادث.

**حدود مهمة:** المراقبة الحالية تختبر استجابة HTTP فقط؛ لا تكشف وحدها كل خطأ داخل واجهة الأداة ولا تصلح الكود تلقائيًا. نتائج الاختبارات المنفصلة هي المرجع للوظائف. سجل Git يحفظ كل commit، بينما ملف الحالة يتحدث تلقائيًا. الإصلاح الذاتي باستخدام AI وإنشاء PR آلي لم يُفعّلا بعد، ولا ينبغي الادعاء بعكس ذلك. لا تُدرج الأسرار أو بيانات D1 الحية في ملفات السجل أو ZIP.
